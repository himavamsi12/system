One biryani order, twelve system design ideas

01

Scalability

How do we survive 8 pm, when traffic is 4× the daily average?

At 3 pm a handful of servers are enough. At 8 pm on a Friday, millions of people open the app at the same moment. The system must grow automatically for dinner and shrink afterwards so we don't pay for idle machines.

In plain words: instead of buying one giant computer, we run many identical copies of each service and add or remove copies as traffic changes. We spread them over three separate data centers (availability zones) in Mumbai so one building losing power doesn't stop dinner.

What we decided decisions

  • All services are stateless: no login or cart kept in a server's memory, so any copy can serve Priya.
  • Scale out app servers horizontally; scale the database up (bigger machine) as long as possible.
  • Run in 3 availability zones, at least 2 copies of everything.
  • Orders and payments are CP (correct over available); menus, ratings and ETAs are AP (always answer, may be slightly old).

Tools we picked stack

  • Cloud in the Mumbai region (ap-south-1), close to users. Alt: GCP, Azure.

  • Packages each service so it runs the same everywhere.

  • Runs the containers, restarts crashed ones, spreads them across zones. Alt: ECS.

  • Autoscaler: adds pods when CPU passes 60%, removes them at night. Alt: KEDA for queue-based scaling.

Friday-night failure what breaks

What happensZone B in Mumbai loses power at 8:10 pm, taking a third of our servers with it.

How we prevent itThe load balancer's health checks drop zone B in seconds. Zones A and C keep 2 copies each, and the autoscaler adds pods there. Because we always run with 50% headroom, users notice nothing.

Say this in the interview"Peak is about 30k reads/s and 400 orders/s. I'll keep services stateless on Kubernetes across three zones with autoscaling, and treat orders as CP and menus as AP."

02

Networking & API design

How does Priya's tap reach our servers, and in what language do they talk?

Different conversations need different styles. Loading a menu is a normal request and answer. Watching a rider move on a map needs the server to push updates. Razorpay telling us "payment succeeded" means another company calls us.

In plain words: DNS is the phone book that finds our address, HTTPS is a sealed envelope for each request, a WebSocket is a phone call that stays open so we can keep talking, and a webhook is another company calling us back when something happens.

# Customer app → API gateway (REST over HTTPS, JSON) GET /v1/restaurants?lat=17.44&lng=78.39&cursor=abc # cursor pagination for the feed GET /v1/restaurants/{id}/menu POST /v1/orders Idempotency-Key: 9f2c-… # retry-safe: never creates 2 orders GET /v1/orders/{id} WSS /v1/orders/{id}/track # live rider position, pushed every 4 s # Razorpay → us (webhook, signed with HMAC) POST /webhooks/razorpay event: payment.captured # Service → service inside the cluster (gRPC, binary, typed) pricing.QuoteService/GetQuote(cart) → { total: 349, delivery_fee: 25 }

What we decided decisions

  • REST for the mobile app: simple, cacheable, easy to debug.
  • WebSocket for live tracking instead of polling every 2 s.
  • gRPC between internal services: faster, strict contracts.
  • Idempotency keys on every payment and order call.
  • Versioned URLs (/v1/) so old app versions keep working.

Tools we picked stack

  • DNS with health checks; can fail over to another region. Alt: Cloudflare DNS.

  • API gateway: checks tokens, rate limits, routes /v1/orders to the order service. Alt: AWS API Gateway, Envoy.

  • Internal calls like order → pricing.

  • Open connection for tracking. Alt: Server-Sent Events, MQTT for riders.

Friday-night failure what breaks

What happensPriya's phone switches from Wi-Fi to 4G mid-payment. The app times out and taps "Place order" again.

How we prevent itBoth requests carry the same Idempotency-Key. The order service stores the key with the first result and returns that same order the second time. One order, one charge.

Say this in the interview"REST with idempotency keys for orders, a WebSocket per active order for tracking, signed webhooks from the payment gateway, and gRPC inside."

03

Load balancing

Which of our 40 servers answers Priya, and what if one is sick?

We run many copies of each service. Something has to pick a copy for every request, skip the broken ones, and keep long-lived tracking connections stable.

In plain words: a load balancer is the receptionist who sends each visitor to a free counter. An L7 balancer reads the request ("this is about orders") and picks the right team. An L4 balancer just connects calls quickly without reading them, which suits millions of open WebSocket connections.

TrafficBalancerAlgorithmWhy
/v1/orders, /v1/menuAWS ALB (L7)Least outstanding requestsSome order calls are slow (payment waits), so send new ones to the least busy pod
Live tracking WebSocketsAWS NLB (L4)Sticky per connectionA connection stays on one server for its whole life; L4 handles millions cheaply
Service → serviceKubernetes Service / EnvoyRound robin with outlier ejectionPods are identical; a pod returning errors is removed automatically
Redis cache keysClient-side consistent hashingHash ringAdding a cache node moves only ~1/N of keys

What we decided decisions

  • Health check GET /healthz every 5 s; 2 failures removes a pod.
  • Connection draining for 30 s on every deploy so no order call is cut mid-way.
  • WebSocket servers share updates through Redis pub/sub, so it doesn't matter which server Priya's connection landed on.

Tools we picked stack

  • Managed L7, spread across zones, never a single point of failure. Alt: Nginx, HAProxy.

  • L4 for WebSockets and huge connection counts.

  • Sidecar proxy that balances gRPC calls between services.

  • Pub/sub fan-out between WebSocket servers.

Friday-night failure what breaks

What happensOne order pod has a memory leak and starts timing out.

How we prevent itIts health check fails, the ALB stops sending it traffic, and Kubernetes restarts it. Requests already in flight are retried once on another pod because order creation is idempotent.

Say this in the interview"ALB at L7 routing by path with least-outstanding-requests, NLB for WebSockets with Redis pub/sub between socket servers, and health checks with connection draining."

04

Caching & CDN

How does the biryani place's menu open in 40 ms?

The restaurant's menu is read by thousands of people every hour but changes maybe twice a day. Reading it from the database every time would waste money and time. But when the kitchen runs out of chicken, the app must stop showing it within seconds.

In plain words: we keep a ready copy of each menu in Redis, which lives in memory and answers in about a millisecond. Photos are copied to CDN servers in Hyderabad itself. When the menu changes, we throw away the old copy so the next person gets the new one.

DataWhere it's cachedTTLHow it's refreshed
Dish photos, app assetsCloudFront CDN30 daysNew photo gets a new file name, so no purge is needed
Menu of a restaurantRedis (cache-aside)10 minDeleted on every change via an event
Restaurants near a locationRedis, keyed by area cell60 sExpires; slightly stale is fine (AP)
Login sessions, cartRedisUntil checkoutWritten directly
Price at checkout, payment statusNever cached–Always read from the database (CP)

What we decided decisions

  • Cache-aside: read Redis, on miss read Postgres and save with a TTL.
  • On update, delete the key rather than overwrite it, to avoid race conditions.
  • Random jitter on TTLs so thousands of keys don't expire in the same second.
  • Expected hit rate ~97%: Postgres sees only 3 in 100 menu reads.

Tools we picked stack

  • In-memory cache with TTLs, replicas and failover (ElastiCache). Alt: Memcached.

  • CDN edges in Indian cities for images and app bundles. Alt: Cloudflare, Akamai.

  • Carries "menu changed" events to the cache invalidator.

Friday-night failure what breaks

What happensA popular restaurant's menu key expires and 5,000 people request it in the same second. All of them miss and hit Postgres at once (a cache stampede).

How we prevent itOnly the first request takes a short Redis lock and rebuilds the menu; the rest wait 50 ms and read the fresh copy. Hot menus are also refreshed shortly before they expire.

Say this in the interview"Menus are read 1000× more than written, so Redis cache-aside with a 10-minute jittered TTL and event-driven invalidation, plus a CDN for images. Checkout prices are never served from cache."

05

Databases

Where does each kind of data live?

Orders need transactions and must never be lost. Rider locations change 40,000 times a second and are useless after a minute. Business dashboards scan billions of rows. No single database is good at all three, so we use the right one for each.

In plain words: a relational database (Postgres) is a strict accountant: perfect records, careful about every change. Redis is a whiteboard: super fast, rewritten constantly. An analytics database is a warehouse built for counting huge piles quickly.

DataDatabaseWhy this oneRejected
Orders, paymentsPostgreSQL (Aurora)ACID transactions, constraints, joins for support toolsMongoDB: weaker multi-row transactions for money
Menus, restaurantsPostgreSQL + Redis cacheRelational data (restaurant → categories → dishes), read-heavyDynamoDB: harder ad-hoc queries for restaurant tools
Live rider locationsRedis GEO40k writes/s, "riders within 3 km" in milliseconds, data can expirePostgres: too many writes for data that lives 60 s
Search indexElasticsearchFull-text, typos, geo-distance filters (chapter 10)SQL LIKE: slow and no relevance ranking
Analytics & reportsClickHouseColumnar, aggregates billions of events in secondsProduction Postgres: reports would slow down orders

What we decided decisions

  • Orders table indexed on (customer_id, created_at) for "my orders" and on (restaurant_id, status) for the kitchen tablet.
  • One primary for writes, read replicas for order history and support screens.
  • When one primary isn't enough, shard by city: Hyderabad's orders never need to join with Mumbai's.
  • Connection pooling, because 400 pods × 20 connections would overwhelm Postgres.

Tools we picked stack

  • Managed Postgres with fast failover to a replica in another zone.

  • Shards Postgres by city when we outgrow one primary. Alt: Vitess (MySQL).

  • Shares a few hundred DB connections among thousands of requests. Alt: RDS Proxy.

  • Analytics fed from Kafka. Alt: BigQuery, Snowflake.

Friday-night failure what breaks

What happensPriya places the order, the app immediately opens "My orders", and it's not there. The read went to a replica that is 200 ms behind.

How we prevent itRead-your-writes: for 5 seconds after a user writes, their reads go to the primary. The order screen also uses the order ID returned by the create call.

Say this in the interview"Postgres for orders with replicas and sharding by city_id later, Redis GEO for rider locations, Elasticsearch for search and ClickHouse for analytics, each chosen by its access pattern."

06

Consistency & distributed transactions

Money, restaurant and rider live in different services. How do they agree?

Placing an order touches four services: create the order, charge ₹349, get the restaurant to accept, and find a rider. Each has its own database, so there is no single transaction that can undo everything if step 3 fails.

In plain words: a saga is a checklist where every step also has an "undo". If the restaurant says no, we go back through the steps we already did and reverse them: refund the money, then cancel the order. A workflow engine remembers where we are even if a server crashes halfway.

What we decided decisions

  • Orchestrated saga: one workflow drives the steps, so the whole flow is visible in one place.
  • Each step is idempotent (safe to run twice) because the engine retries after crashes.
  • Order status is a state machine: PENDING → PAID → ACCEPTED → RIDER_ASSIGNED → PICKED_UP → DELIVERED, or CANCELLED.
  • Strong consistency only where needed: the payment record and order status. Everything else is eventual.

Tools we picked stack

  • Durable workflows with retries, timers ("restaurant must accept in 3 min") and compensation. Alt: AWS Step Functions.

  • Payment step and refund compensation; supports idempotent requests.

  • Stores order state; row lock prevents two status updates at once.

Friday-night failure what breaks

What happensPriya paid, but the restaurant tablet goes offline and never accepts.

How we prevent itThe workflow has a 3-minute timer. When it fires, the saga runs compensations: refund ₹349 via Razorpay, mark the order cancelled, notify Priya with a coupon. No money is stuck.

Say this in the interview"An orchestrated saga in Temporal: create order, charge, restaurant accept with a timeout, assign rider. Each step is idempotent and has a compensating action like refund or cancel."

07

Queues & event streaming

Once the order exists, who tells everyone else?

After an order is placed, at least five things must happen: ping the restaurant tablet, start finding a rider, send Priya a push notification, update analytics, and give a loyalty point. If the order service called all five directly, one slow system would slow down every order.

In plain words: the order service writes one announcement, "Order 48213 was placed", on a shared noticeboard (Kafka) and moves on. Each team reads the noticeboard at its own pace. If a team is down for 10 minutes, the notices wait for it.

What we decided decisions

  • Topic order-events keyed by order_id, so one order's events stay in order.
  • Transactional outbox: the event is saved in the same database transaction as the order, then relayed to Kafka. The event can never be lost.
  • Consumers are idempotent (Kafka delivers at least once).
  • 3 retries with backoff, then a dead-letter topic and an alert.

Tools we picked stack

  • Durable event log, replayable for 7 days (Amazon MSK). Alt: RabbitMQ, SQS + SNS.

  • Reads the outbox table changes and publishes them to Kafka.

  • Push notifications to Android and iOS. Alt: OneSignal.

  • Analytics consumer.

Friday-night failure what breaks

What happensThe push notification provider slows down; the notifications consumer falls 50,000 events behind.

How we prevent itNothing else is affected because each consumer group has its own offset. We alert on consumer lag and autoscale notification workers on queue depth. Orders and rider dispatch keep moving.

Say this in the interview"Order creation is synchronous; everything after it is asynchronous through Kafka with an outbox for reliability, idempotent consumers, and a DLQ."

08

Architecture

How do we split the app into services, and why?

With 300 engineers working on search, payments, dispatch and offers, one shared codebase would mean everyone waits on everyone to deploy. Some parts, like location tracking, also need 20× more machines than others.

In plain words: we split the system along business lines. Each service is owned by one team, has its own database, and can be released on its own. They talk through the gateway, direct calls for questions that need an answer now, and events for news.

What we decided decisions

  • One service per business capability; no service reads another's tables.
  • Synchronous gRPC only when the answer is needed now (order asks pricing for the total).
  • Events for everything else (order placed, rider assigned).
  • A small startup version of this app would be a modular monolith first; we split as teams grow.

Tools we picked stack

  • High-throughput services: location, dispatch, orders.

  • BFF and menu services that shape JSON for the app.

  • Service mesh: mTLS, retries and traffic splits between services. Alt: Linkerd.

  • All infrastructure defined as code.

Friday-night failure what breaks

What happensThe offers service is slow, and because the order service calls it, every checkout waits.

How we prevent itStrict timeouts (300 ms) and a fallback of "no offer applied" so checkout continues. Non-essential calls are never on the critical path.

Say this in the interview"Services by domain: catalog, search, cart, order, payment, dispatch, location, notification. Each owns its data, uses gRPC for direct queries and Kafka for events."

09

Resilience

IPL final, 10:45 pm: traffic jumps 10× and Razorpay starts failing

Everyone orders food at the same moment, bots hammer the offers API, and the main payment gateway returns errors under its own load. The system must protect itself, degrade gracefully, and keep taking money.

In plain words: a rate limiter is a turnstile that lets each person through only so fast. A circuit breaker is a fuse: when the payment gateway keeps failing, stop calling it for a while and switch to the backup. Feature flags let us switch off nice-to-have features so the essentials have room.

What we decided decisions

  • Rate limit at the gateway: 20 requests/s per user, 5 order attempts/min, stricter per IP for login.
  • Circuit breaker on each payment gateway: opens at 30% errors in 20 s, half-opens after 30 s.
  • Load shedding: recommendations and "reorder" carousels switch off first; search, menu, checkout stay on.
  • Retries only with backoff + jitter, and only for idempotent calls.

Tools we picked stack

  • Rate-limit plugin with counters in Redis shared by all gateway nodes.

  • Circuit breakers, timeouts, bulkheads in service code. Alt: Istio outlier detection.

  • Feature flags to switch off heavy features instantly. Alt: LaunchDarkly.

  • Blocks bot and attack traffic before it reaches us.

Disaster recovery bigger failure

What happensThe entire Mumbai region has a major outage.

How we prevent itA warm standby in Hyderabad region (ap-south-2) with replicated databases. Route 53 fails over DNS. Target: RPO under 1 minute of data, RTO under 15 minutes. We rehearse it every quarter.

Say this in the interview"Token-bucket rate limits at the gateway, circuit breakers with a backup payment gateway, feature-flag load shedding of non-essentials, and a warm-standby region with tested failover."

10

Storage, search & geo

Photos, "biryani near me", and finding Ravi 1.2 km away

Three special problems: storing millions of dish photos, searching dishes by name with typos within a delivery radius, and finding the closest free rider among 160,000 moving ones in milliseconds.

In plain words: photos go to a huge cheap file store (S3), never the database. Search uses an index like the one at the back of a book. For riders, we cut the map into small hexagon tiles; to find riders near the restaurant we only look in its tile and the tiles touching it.

What we decided decisions

  • Restaurants upload photos directly to S3 using a 5-minute presigned URL.
  • Images resized to 3 sizes and WebP once, then served by CDN.
  • Search index fed by change-data-capture from Postgres, never written by app code.
  • Rider locations: H3 hexagon cell per rider in Redis, expiring after 60 s if the rider goes silent.

Tools we picked stack

  • Object storage for photos, invoices, backups.

  • Resizes each uploaded image. Alt: imgproxy, Cloudinary.

  • Fuzzy search ("biriyani" finds biryani) + geo_distance filter. Alt: OpenSearch, Typesense.

  • Hexagonal grid to bucket locations. Alt: geohash, Redis GEOSEARCH.

Friday-night failure what breaks

What happensA restaurant marks itself closed, but search still shows it for a while.

How we prevent itThe CDC pipeline updates the index in about 2 s. As a safety net, the menu service checks the live "open" flag before showing the menu, so a stale search result can never lead to an order.

Say this in the interview"Presigned uploads to S3 served via CDN, Elasticsearch fed by CDC for search, and H3 cells in Redis for nearest-rider lookup."

11

Security

Proving it's really Priya, and keeping her money safe

Users log in with a phone OTP. Restaurants, riders, support staff and customers must see different things. Card and UPI details must never touch our servers, and nobody should be able to fake a "payment succeeded" message.

In plain words: after the OTP, Priya gets a signed digital pass (JWT) that expires in 15 minutes. The gateway checks the signature on every request. The order service still checks that order 48213 actually belongs to her. Razorpay handles the card or UPI details so we only ever see a token.

What we decided decisions

  • OTP login, rate-limited to 3 attempts per 10 minutes per phone number.
  • 15-min access JWT + rotating refresh token in secure storage on the phone.
  • Roles: customer, restaurant, rider, support, admin; plus ownership checks on every order.
  • Verify every Razorpay webhook's HMAC signature before trusting it.
  • TLS everywhere, mTLS between services, secrets in Vault.

Tools we picked stack

  • Stateless signed tokens the gateway verifies without a database call.

  • SMS OTP delivery. Alt: Twilio, Gupshup.

  • PCI-compliant checkout; we never store card numbers.

  • Stores and rotates API keys and DB passwords. Alt: AWS Secrets Manager.

Attack attempt what breaks

What happensSomeone changes /v1/orders/48213 to 48214 to see another person's address (IDOR).

How we prevent itThe order service compares the order's customer_id with the token's user ID and returns 403. Order IDs exposed to apps are random, not sequential.

Say this in the interview"OTP login issuing short-lived JWTs verified at the gateway, RBAC plus ownership checks per resource, tokenized payments, signed webhooks, and mTLS internally."

12

Observability & deployment

How do we know orders are flowing, and ship changes without breaking dinner?

With dozens of services, "the app is slow" could come from anywhere. We need to see the health of every hop, get woken up only for real problems, and release new code so carefully that a bug reaches very few users.

In plain words: metrics are the speedometer, logs are the diary, traces are a GPS track of one request across all services. A canary release sends 5% of users to the new version first and automatically rolls back if their errors go up.

What we decided decisions

  • Golden signals for every service: latency, traffic, errors, saturation.
  • The most important metric is a business one: orders per minute by city, compared to last Friday.
  • Alert on SLO burn rate (e.g. checkout success < 99.5%), not on CPU.
  • Every deploy is a canary: 5% → 25% → 100% over 30 minutes, auto-rollback on errors.

Tools we picked stack

  • One standard SDK for metrics, logs and traces.

  • Metrics storage and alert rules.

  • Dashboards; with Loki for logs and Tempo for traces. Alt: Datadog for all-in-one.

  • Canary releases with automatic analysis.

  • Pages the on-call engineer.

Friday-night failure what breaks

What happensVersion 42 of the order service has a bug that fails UPI payments in Telugu-language sessions.

How we prevent itOnly 5% of users get v42. Argo sees their checkout success drop below v41's and rolls back in 3 minutes. A trace shows the exact failing call for the fix.

Say this in the interview"OpenTelemetry everywhere into Prometheus, Loki and Tempo with Grafana; alerts on SLO burn rate and orders per minute; canary deploys with automatic rollback."

Case study for learning. The design and tools are typical industry choices for a food delivery platform, not a description of any company's actual internal systems. Numbers are estimates.
