01

Foundations

Scalability, availability and the core trade-offs

Scalability means your system keeps working well as users grow from 100 to 100 million. Every other topic in this manual is a technique for scaling, so learn this vocabulary first.

Think of it likea dosa stall. When the queue grows you can buy a bigger tawa and hire a faster cook (vertical scaling), or open three more counters with three cooks (horizontal scaling). The bigger tawa has a limit. More counters can keep growing, but now you need someone at the entrance sending people to the shortest line.

The vocabulary you must own

  • Latency: time for one request (e.g. 120 ms). Throughput: requests handled per second (QPS).
  • Availability: % of time the system works. 99.9% = 8.7 h down per year; 99.99% = 52 min per year.
  • SLA / SLO / SLI: SLI is the measurement (p99 latency), SLO is your internal target (p99 < 200 ms), SLA is the promise in the contract with penalties.
  • Single point of failure (SPOF): any component that, if it dies, takes the whole system down. Remove them with redundancy.
  • Stateless vs stateful: a stateless server keeps nothing between requests, so any copy can serve any user. Store sessions in Redis or a JWT.
  • p50 / p99: half of requests are faster than p50; 99% faster than p99. Always talk about p99, because the slow tail is what users notice.

CAP theorem in plain words

  • When the network between your servers breaks (a partition), you must choose:
  • Consistency (CP): refuse requests rather than return stale data. Used for bank balances, inventory, bookings.
  • Availability (AP): keep answering even if data may be a little old. Used for likes, feeds, view counts.
  • Partitions always happen in real networks, so it's really a choice between C and A during failure.
  • PACELC adds: even with no failure (Else), you trade Latency vs Consistency. Waiting for 3 replicas is safer but slower.

What breaks, and how we prevent it

One server dies and the site goes down

Run at least 2 of everything across 2+ availability zones. Remove every SPOF.

Traffic spike on sale day (Big Billion Day)

Autoscaling groups, pre-warming capacity, caching, queueing writes, rate limiting.

Sessions lost when a user hits a different server

Make servers stateless: sessions in Redis or signed JWT tokens.

Whole region goes down (AWS Mumbai outage)

Multi-region deployment with DNS failover; replicate data across regions.

Interview depth

Vertical or horizontal scaling: which would you use? Beginner

Both. Start vertical because it's simple. Make app servers stateless so they scale horizontally behind a load balancer. The database is the hard part to scale horizontally, so delay sharding until replicas and caching are not enough.

Is a payment system CP or AP? A news feed? Intermediate

Payments are CP: showing a wrong balance or charging twice is worse than a "try again" error. A feed is AP: a post appearing 2 seconds late is fine, but the feed must never be blank. Good answers say a single system often mixes both: the cart is AP, the checkout is CP.

Estimate the servers needed for 50 M daily active users. Intermediate

50 M users × 20 requests/day = 1 B requests/day ÷ 10⁵ s ≈ 10k QPS average, ~30k peak. At ~2k QPS per server that's 15 servers, so plan ~25 for headroom and zone failure. State assumptions out loud; the method matters more than the number.

How do you go from 99.9% to 99.99% availability? Senior

Availability of components in series multiplies (0.999 × 0.999 = 0.998), so remove serial dependencies, add redundancy in parallel, deploy across zones and regions, use canary releases (most outages come from deploys), and set up automatic failover with health checks.

Say this in the interview: "Let me first estimate scale: users, QPS at peak, read-to-write ratio, and storage growth. That tells me where the bottleneck will be."

02

How requests travel

Networking, protocols and API design

Before any server does work, a request has to find it and talk to it. This topic covers the journey of one click and the styles of API you can expose.

Think of it likeposting a letter. DNS is the phone book that turns "swiggy.com" into an address. TCP is registered post: guaranteed delivery, in order. UDP is a postcard: fast, may get lost. HTTP is the language written in the letter. TLS is the sealed envelope.

Good API design rules

  • Nouns, not verbs: POST /orders, not /createOrder.
  • Pagination: cursor-based (?after=abc123) for feeds; offset (?page=3) breaks when new items are inserted.
  • Idempotency key: client sends a unique Idempotency-Key header so a retried payment isn't charged twice.
  • Versioning: /v1/ in the path or a header, so old mobile apps keep working.
  • Correct status codes: 200 OK, 201 Created, 400 bad input, 401 not logged in, 403 not allowed, 404, 409 conflict, 429 rate limited, 500/503 server errors.

What breaks, and how we prevent it

Client retries a timed-out payment and pays twice

Idempotency keys stored for 24 h; server returns the first result for repeated keys.

Mobile app loads 30 API calls per screen

Backend-for-frontend (BFF) or GraphQL to aggregate; HTTP/2 multiplexing.

1 M WebSocket connections overload servers

Dedicated connection servers, sticky routing, Redis pub/sub to fan out messages between them.

Interview depth

What happens when you type swiggy.com and press Enter? Beginner

Browser checks its DNS cache, then asks a resolver which returns an IP. It opens a TCP connection (3-way handshake), then a TLS handshake to agree on encryption keys. It sends an HTTP GET. The request hits a CDN or load balancer, goes to an app server, which may query cache and database, and returns HTML. The browser then fetches JS, CSS and images (mostly from the CDN) and renders.

How would you build live delivery-partner tracking? Intermediate

The rider app sends GPS every 3–5 s over HTTP or MQTT to a location service that writes the latest position to Redis. The customer app holds a WebSocket (or SSE) to a gateway that subscribes to that order's location channel and pushes updates. Polling every 5 s also works at small scale and is simpler; mention the trade-off.

REST vs gRPC for internal services? Senior

gRPC is faster (binary, HTTP/2 multiplexing), has strict typed contracts, and supports streaming, so it suits high-volume internal calls. REST is easier to debug, works in browsers, and is better for public APIs. Many companies use REST/GraphQL at the edge and gRPC inside.

Say this in the interview: "Let me define the API first: POST /v1/orders with an idempotency key, GET /v1/orders/{id}, and a WebSocket channel for status updates."

03

Spreading the traffic

Load balancing

A load balancer sits in front of many servers and decides which one handles each request. It's what makes horizontal scaling and high availability possible.

Think of it likethe security guard at a bank who looks at the counters and sends you to the one with the shortest queue, and who stops sending people to a counter whose clerk has gone on break.

Layer 4 vs Layer 7

  • L4 (transport): looks only at IP and port. Very fast, can't read the URL. Good for raw TCP, databases, game servers.
  • L7 (application): reads HTTP: path, headers, cookies. Can route /api/* to API servers and /images/* elsewhere, terminate TLS, do A/B splits.
  • Most web systems use an L7 load balancer at the edge.

Routing algorithms

  • Round robin: 1, 2, 3, 1, 2, 3. Fine when servers and requests are similar.
  • Weighted round robin: a bigger server gets 2× the share.
  • Least connections: best when some requests are slow (uploads, reports).
  • IP hash / sticky sessions: same user always hits the same server. Needed for WebSockets; avoid otherwise.
  • Consistent hashing: maps keys to servers on a ring so adding a server only moves ~1/N keys. Used for caches and sharded data.

What breaks, and how we prevent it

A server crashes but still receives traffic

Active health checks (GET /health every 5 s, remove after 2–3 failures) plus passive checks on error rates.

The load balancer itself fails

Active-passive pair with a floating IP (keepalived), or a managed LB spread across zones.

Deploying kills users' in-flight requests

Connection draining: stop sending new requests, wait 30 s for existing ones to finish, then stop the server.

Sticky sessions overload one server

Store session state externally (Redis) and turn stickiness off.

A new server gets flooded before its cache is warm

Slow start: ramp its weight up over a few minutes.

Interview depth

Why do we need a load balancer? Beginner

To spread load across servers (scalability), to stop sending traffic to dead servers (availability), and to give clients one stable address while servers come and go (flexibility for deploys and autoscaling).

Explain consistent hashing and why it matters. Intermediate

With hash(key) % N, changing N from 4 to 5 remaps ~80% of keys, which empties every cache at once. Consistent hashing places servers and keys on a ring; each key goes to the next server clockwise. Adding a server only takes keys from its neighbour (~1/N). Virtual nodes (each server placed 100–200 times on the ring) keep the load even. Used in DynamoDB, Cassandra, and memcached clients.

How would you route users globally? Senior

GeoDNS or anycast sends users to the nearest healthy region; within a region, an L7 load balancer spreads across zones; inside, Kubernetes or a service mesh balances across pods. Each layer has health checks, so a failed region is removed from DNS automatically.

Say this in the interview: "I'll put a redundant L7 load balancer in front of stateless app servers, using least-connections with health checks, so I can autoscale and lose a server without users noticing."

04

Speed for free

Caching and CDNs

A cache keeps a copy of frequently used data in fast memory so you don't recompute it or hit the slow database every time. It's the single biggest performance win in most designs.

Think of it likekeeping the 20 spices you use daily on the kitchen counter instead of walking to the storeroom each time. The counter is small, so you keep only what you use most, and you refill when something runs out or goes stale.

What breaks, and how we prevent it

Stale data: price changed but users see old price

Delete the cache key on every write (not update), short TTLs, or publish change events that invalidate keys.

Cache stampede: a hot key expires and 10,000 requests hit the DB at once

Lock so only one request rebuilds the value (others wait), refresh ahead of expiry, add random jitter to TTLs.

Hot key: one celebrity profile gets 1 M reads/s on one Redis node

Replicate the key across nodes (key#1…key#10), add a small in-process cache in front.

Cache penetration: requests for IDs that don't exist always miss

Cache the "not found" result briefly, or use a Bloom filter to reject unknown IDs.

Cache cluster restarts empty and the DB collapses

Redis replicas with automatic failover (Sentinel/Cluster), warm the cache before taking traffic, rate limit DB access.

Cache fills up

Eviction policy: LRU (least recently used) by default, LFU for stable popularity, TTL on everything.

Interview depth

What would you cache in an e-commerce site? Beginner

Product pages and images (CDN plus Redis), category listings, sessions and cart (Redis), search suggestions. Don't cache inventory counts at checkout or payment status, because those must be exact.

On update, why delete the cache key instead of updating it? Intermediate

Two concurrent writers can update the DB in order A then B but the cache in order B then A, leaving the cache wrong forever. Deleting means the next read loads the true value from the DB. The remaining risk window is tiny; delayed double-delete or change-data-capture closes it.

How do you size a cache? Intermediate

Use the 80/20 rule: 20% of items get 80% of traffic. If you have 10 M products × 2 KB = 20 GB, caching the hot 20% needs ~4 GB plus overhead, so one 8–16 GB Redis node with a replica fits.

How does a CDN know when content changes? Senior

Either TTL-based expiry, explicit purge API calls on deploy, or (best) content-hashed file names like app.3f9a2c.js, so new content has a new URL and old files can be cached forever.

Say this in the interview: "Reads are 100× writes here, so I'll put Redis in front of the database with cache-aside, a 5-minute TTL with jitter, and delete-on-write. Static assets go through a CDN."

05

Where data lives

Databases: choosing, replicating, sharding

The database is almost always the bottleneck and the hardest thing to change later. Interviewers spend the most time here: which database, how it's modelled, and how it scales.

Think of it likea library. An index is the catalogue that tells you which shelf a book is on. Replication is printing photocopies of the catalogue so many people can read at once. Sharding is splitting the library into branches by author name A–H, I–P, Q–Z when one building can't hold everything.

Core concepts

  • ACID: Atomic (all or nothing), Consistent (rules hold), Isolated (transactions don't see each other's half-done work), Durable (survives crash).
  • Index: a sorted lookup structure (B-tree) so WHERE email = ? doesn't scan 100 M rows. Speeds reads, slows writes slightly.
  • Composite index on (user_id, created_at) serves "this user's latest orders" in one lookup. Column order matters.
  • B-tree vs LSM-tree: B-trees (Postgres) are great for reads; LSM-trees (Cassandra, RocksDB) buffer writes in memory and flush sequentially, great for write-heavy loads.
  • Normalization avoids duplicate data; denormalization copies data (e.g. store author name on each post) to avoid joins at read time.
  • Connection pooling (PgBouncer, RDS Proxy): databases handle only a few hundred connections; a pool shares them across thousands of app requests.

Sharding strategies

  • Hash-based: hash(user_id) % N. Even spread; range queries across users are hard. Use consistent hashing so you can add shards.
  • Range-based: users A–H on shard 1. Range queries easy; hot spots if one range is popular.
  • Geo-based: Indian users in Mumbai, EU users in Frankfurt. Good for latency and data laws.
  • Directory-based: a lookup table says which shard holds each tenant. Flexible, but the directory must be highly available.
  • Choosing the shard key is the big decision: pick the key most queries filter by (user_id, tenant_id), with high cardinality and even load.
  • Tools: Vitess (MySQL, used by YouTube, Slack), Citus (Postgres), MongoDB and Cassandra shard natively.

What breaks, and how we prevent it

Replication lag: user updates profile, refreshes, sees old data

Read-your-writes: read from primary for a few seconds after a user's write, or route that user's reads to primary.

Primary database dies

Automatic failover: promote a replica (RDS Multi-AZ, Patroni). Synchronous replica in another zone avoids losing data.

Slow queries as the table grows

Add indexes (check with EXPLAIN), avoid SELECT *, fix N+1 queries, archive old rows, partition by date.

Hot shard: one big seller's data overloads one shard

Better shard key, split hot tenant to its own shard, add a salt to the key.

Cross-shard queries and joins become slow

Shard by the key you join on, denormalize, or keep a separate read model (search index, warehouse) for global queries.

Accidental delete or corrupt data

Point-in-time recovery backups, tested restores, soft deletes, and delayed replicas.

Interview depth

SQL or NoSQL for a URL shortener? Beginner

It's a simple key → URL lookup with billions of rows and very high reads, no joins. A key-value store like DynamoDB or Cassandra scales easily. Postgres also works fine up to hundreds of millions of rows. Either is acceptable if you justify it with access patterns.

How do you prevent two people booking the same seat? Intermediate

Use a transaction with a row lock: SELECT … FOR UPDATE on the seat, check it's free, update it. Or optimistic locking: UPDATE seats SET status='held', version=v+1 WHERE id=? AND version=v; if 0 rows change, someone else got it. Add a temporary hold with expiry (10 min) in Redis while payment happens.

What are isolation levels and which anomalies do they stop? Senior

Read Committed (Postgres default) prevents dirty reads. Repeatable Read prevents non-repeatable reads. Serializable prevents write skew and phantoms but is slower and retries more. Pick the lowest level that's correct, and use explicit locks for the critical paths.

How would you shard a chat app's messages? Senior

Shard by conversation_id so all messages in a chat are on one shard and can be read in order with one query. Within a shard, cluster by (conversation_id, message_id) where message_id is time-sortable (Snowflake ID). This is exactly how Discord stores messages in ScyllaDB.

Say this in the interview: "Orders need transactions, so Postgres with a primary and two read replicas. I'll index on (user_id, created_at). If writes outgrow one primary, I'll shard by user_id with consistent hashing."

06

Many machines, one truth

Consistency and distributed systems

Once data lives on several machines, they can disagree. This topic is about how machines agree, how strongly they must agree, and how to do a multi-step operation across services without a single database transaction.

Think of it likea family WhatsApp group deciding on dinner. Strong consistency: nobody orders until everyone replies. Eventual consistency: everyone orders on their own and the group sorts it out later. A quorum: order once a majority agrees. A leader: Amma decides and everyone follows.

Consistency levels (strong → weak)

  • Linearizable / strong: every read sees the latest write, as if there's one copy. Bank balance, seat booking, leader election.
  • Sequential / causal: everyone sees related events in the same order (a reply never shows before the message it answers). Comments, chat.
  • Read-your-writes: you always see your own updates, even if others see them a bit later. Profile edits.
  • Monotonic reads: once you see a value, you never see an older one. Pin a user to one replica.
  • Eventual: replicas converge "soon". Like counts, view counts, DNS, product reviews.

Key mechanisms

  • Consensus (Raft, Paxos): a majority of nodes agree on each change and elect a leader. Survives losing a minority (3 nodes tolerate 1 failure, 5 tolerate 2). Powers etcd, ZooKeeper, CockroachDB, Kafka KRaft.
  • Leader election: only one node acts as primary or runs the cron job; others take over if its lease expires.
  • Two-phase commit (2PC): coordinator asks all participants "can you commit?", then "commit". Strong but slow and blocks if the coordinator dies. Rare across microservices.
  • Saga: chain of local transactions with compensating undo steps. Orchestrated (central coordinator like Temporal) or choreographed (services react to events).
  • Distributed lock: Redis SET key NX PX 30000 (Redlock) or etcd/ZooKeeper leases, with fencing tokens so a paused old holder can't write.
  • Clocks: machine clocks drift, so use logical clocks (Lamport, vector clocks) or hybrid clocks to order events. Snowflake IDs embed time for sortable IDs.
  • Gossip & heartbeats: nodes tell each other who's alive (Cassandra, Consul).

What breaks, and how we prevent it

Split brain: network splits and two nodes both think they're leader

Majority quorum (need 2 of 3 to lead), leases with timeouts, fencing tokens on writes.

Payment charged but order never created

Saga with compensations, plus the outbox pattern (topic 7) so the event is never lost.

Same message processed twice after a retry

Idempotent handlers: store processed message IDs, use upserts, unique constraints.

Lock holder pauses (GC), lock expires, two workers write

Fencing token: storage rejects writes with an older token number.

Clock skew orders events wrongly

Don't rely on wall clocks for ordering; use sequence numbers, logical clocks, or a single sequencer.

Interview depth

What is eventual consistency? Give an example where it's fine and one where it's not. Beginner

Replicas may briefly differ but converge if writes stop. Fine: Instagram like counts. Not fine: the last ticket for a concert, where two people must not both get it.

Why does a Raft cluster have an odd number of nodes? Intermediate

It needs a majority to make progress. 3 nodes tolerate 1 failure, 4 nodes still tolerate only 1 (majority is 3), so the 4th adds cost without resilience. 5 tolerate 2.

How do you keep data consistent across microservices without 2PC? Senior

Each service owns its data and commits locally. Publish events reliably with the transactional outbox (write event to an outbox table in the same transaction, a relay sends it to Kafka). Coordinate multi-step flows with a saga that has compensating actions. Make every consumer idempotent. Accept eventual consistency and design the UI around it ("Order placed, confirming…").

How does Google Docs let two people type at once? Senior

Operational Transformation (Google Docs) or CRDTs (Figma-like, Yjs): each edit is an operation that can be transformed or merged so every client ends with the same text regardless of the order edits arrive. A server orders operations and broadcasts them over WebSockets.

Say this in the interview: "Seat inventory needs strong consistency, so it goes through one primary with row locks. The rest of the order flow is a saga with compensations, and the feed and notifications are eventually consistent."

07

Do it later, do it reliably

Message queues and event streaming

A queue lets one part of the system hand work to another without waiting for it. The user gets a fast response, slow work happens in the background, and spikes are absorbed instead of crashing things.

Think of it likea restaurant order slip rail. The waiter clips the order and goes back to customers. Cooks pick slips at their own speed. If 50 orders arrive at once, slips pile up on the rail, but nobody is turned away and nothing is forgotten.

Queue vs stream vs pub/sub

  • Message queue (RabbitMQ, SQS): each message goes to one worker and is deleted when done. Task distribution: send email, resize image, generate invoice.
  • Event stream / log (Kafka, Kinesis): messages are kept for days; many independent consumers read at their own pace and can replay. Event-driven systems, analytics, activity feeds.
  • Pub/sub (Redis pub/sub, SNS, Google Pub/Sub): one message fans out to all subscribers. Notifications, cache invalidation, chat fan-out.

Delivery guarantees

  • At-most-once: may lose messages, never duplicates. Metrics where a gap is OK.
  • At-least-once: never lost, may duplicate. The usual default. Make consumers idempotent.
  • Exactly-once: Kafka offers it within Kafka via transactions; end to end you achieve it as at-least-once + idempotent processing.
  • Ordering: Kafka orders only within a partition, so choose the partition key carefully (order_id, user_id). SQS FIFO orders within a message group.

What breaks, and how we prevent it

Worker crashes mid-task and the job is lost

Acknowledge only after success; unacked messages return to the queue after a visibility timeout.

Duplicate processing sends 2 emails or charges twice

Idempotency: dedupe table of processed message IDs, unique constraints, upserts.

A bad message fails forever and blocks the queue

Retry with exponential backoff, then move to a dead-letter queue and alert.

DB commit succeeds but publishing the event fails

Transactional outbox: write the event to an outbox table in the same DB transaction; a relay (Debezium) publishes it.

Consumers fall behind (consumer lag grows)

Monitor lag, add partitions and consumers, batch processing, autoscale workers on queue depth.

Producers flood the system during a spike

Back-pressure: bounded queues, rate limits at the producer, queue absorbs the burst while workers drain at a steady rate.

Interview depth

Why add a queue between upload and video processing? Beginner

Encoding takes minutes. The upload API returns immediately ("processing"), puts a job in the queue, and a pool of workers encodes at their own pace. If 10× uploads arrive, the queue grows instead of servers falling over, and failed jobs are retried.

Kafka or RabbitMQ? Intermediate

Kafka when you need very high throughput, ordering per key, retention and replay, or several teams consuming the same events. RabbitMQ when you need flexible routing, per-message acknowledgement, priorities and simpler operations for task queues. SQS when you just want a managed queue on AWS.

How would you send a notification to 10 M followers when a celebrity posts? Senior

The post service publishes one event. A fan-out service reads follower IDs in batches and enqueues delivery jobs partitioned by user. Workers call APNs/FCM with rate limits per provider, with retries and a DLQ. For feeds, celebrities use fan-out-on-read (merge their posts at read time) instead of writing to 10 M inboxes.

Say this in the interview: "Placing the order is synchronous. Everything after it (email, invoice, analytics, rider assignment) is asynchronous through Kafka, keyed by order_id, with idempotent consumers and a dead-letter queue."

The shape of the system

Architecture patterns

How you split the system into pieces: one big application, many small services, functions that run on demand, or services that talk through events. Each shape suits a different team size and scale.

Think of it likea kitchen. A monolith is one chef cooking everything: simple, until the restaurant gets huge. Microservices are stations (tandoor, chinese, desserts) each with its own cook and pantry, working independently and passing tickets. More throughput, but now you need coordination.

What breaks, and how we prevent it

Interview depth

Monolith or microservices for a new startup? Beginner

Monolith (ideally modular). It's faster to build, test and deploy with a small team. Microservices solve organizational and scaling problems the startup doesn't have yet, while adding network and data complexity.

How do you split a monolith? Intermediate

Strangler fig pattern: put a gateway in front, carve out one well-bounded domain at a time (e.g. notifications, then payments), route its traffic to the new service, migrate its data, and retire the old code. Start with parts that change often or scale differently.

When would you use CQRS? Senior

When reads need a very different shape than writes, for example an order system writes normalized rows in Postgres but the seller dashboard reads pre-aggregated views in Elasticsearch or a materialized table. Events from the write side update the read side, which can lag by seconds.

Say this in the interview: "I'll start with services for the parts that scale differently, like the location service and the order service, behind an API gateway, communicating through Kafka events, each owning its database."

Failing gracefully

Resilience: rate limiting, circuit breakers, retries, disaster recovery

Everything fails eventually: servers, networks, third-party APIs, whole regions. Resilience patterns make sure one failure stays small instead of spreading through the whole system.

Think of it likethe electrical fuse box in your house. A rate limiter is the meter that caps how much power one appliance can draw. A circuit breaker trips when something shorts, so the fault doesn't burn down the whole house, and you try switching it back on after a while.

Rate limiting algorithms

  • Token bucket: tokens refill at a steady rate; each request spends one. Allows short bursts. Most common (AWS, Stripe).
  • Leaky bucket: requests drain at a fixed rate, extras wait or drop. Smooth output, used for traffic shaping.
  • Fixed window: 100 requests per minute, counter resets on the minute. Simple, but 200 can slip through at the boundary.
  • Sliding window log / counter: counts over the last 60 s exactly or approximately. Fairer, slightly more memory.
  • Return 429 with a Retry-After header so clients know when to try again.

The resilience toolkit

  • Timeouts on every network call. Without them, threads pile up waiting forever.
  • Retries with exponential backoff + jitter: wait 100 ms, 200 ms, 400 ms… plus randomness, so clients don't retry in sync. Only retry idempotent operations.
  • Bulkheads: separate thread or connection pools per dependency, so a slow payment API can't use up the pool needed for search.
  • Graceful degradation: if recommendations fail, show "popular items" instead of an error page.
  • Load shedding: when overloaded, drop low-priority traffic first (analytics before checkout).
  • Disaster recovery: RPO = how much data you can lose; RTO = how long you can be down. Options from cheapest to fastest: backup & restore → pilot light → warm standby → active-active.

Interview depth

Why do we need rate limiting? Beginner

To protect the system from overload (spikes, bugs in clients, bots), to prevent abuse (brute force, scraping), to keep usage fair between customers, and to control cost on paid downstream APIs.

Design a distributed rate limiter. Intermediate

Run it at the API gateway. For each request, build a key like rl:{user_id}:{minute}, run an atomic Redis Lua script that refills/decrements a token bucket and returns allow or deny. Redis Cluster shards keys. If Redis is down, fail open for most endpoints (allow) and fail closed for sensitive ones like login. Return headers: X-RateLimit-Remaining, Retry-After.

How do retries make outages worse, and how do you stop it? Senior

With 3 retries at each of 4 layers, one user request can become 3⁴ = 81 calls on the deepest service. Retry at only one layer, use backoff with jitter, cap retries with a budget, honour Retry-After, and let circuit breakers stop calls to a failing service entirely.

Say this in the interview: "Every external call gets a timeout, retries with jittered backoff, and a circuit breaker with a fallback. The gateway rate-limits per user with a Redis token bucket."

Files, search and special structures

Object storage, search and clever data structures

Images, videos and documents don't belong in a database, and "find products like 'red shose'" can't be answered with SQL LIKE. This topic covers where big files go, how search engines work, and a few data structures interviewers love.

Think of it likea godown and an index card box. Big items (files) go to a cheap, huge godown (object storage), and the database only keeps the slip saying where each item is. A search index is the back-of-book index: for every word, the list of pages it appears on.

Storage types

  • Object storage (S3, Cloudflare R2, GCS): files addressed by key, virtually unlimited, 11 nines durability, cheap. Images, videos, backups, exports.
  • Block storage (EBS): a virtual hard disk attached to one server. Databases run on it.
  • File storage (EFS, NFS): shared folders mounted by many servers.
  • Storage tiers: S3 Standard → Infrequent Access → Glacier for old data. Lifecycle rules move data automatically.
  • Large uploads: multipart upload in chunks (5–100 MB) with resume; Dropbox also dedupes chunks by hash.
  • Data lake / warehouse: raw files in S3 (lake) or structured analytics tables (Snowflake, BigQuery, Redshift, ClickHouse) for reporting, never on your production DB.

How search works

  • Inverted index: "red" → [doc 4, 9, 22], "shoes" → [doc 9, 22, 31]. Intersect lists to find documents with both words, instantly.
  • Analyzers: lowercasing, stemming ("running" → "run"), synonyms, n-grams for autocomplete.
  • Fuzzy matching: edit distance handles typos like "shose".
  • Ranking: BM25 relevance score plus business signals (popularity, rating, stock).
  • Autocomplete: a trie or prefix index of popular queries, cached heavily; results computed offline from search logs.
  • Semantic search: embeddings in a vector index (pgvector, Pinecone) find meaning, not just words; often combined with keyword search (hybrid).

Interview depth

Why not store images in the database? Beginner

It bloats the DB, makes backups huge and slow, wastes expensive DB I/O, and can't be served by a CDN easily. Store the file in object storage and keep only its URL and metadata in the DB.

How would you find drivers within 2 km? Intermediate

Encode locations as geohashes (or H3 cells). Drivers update their cell in Redis (GEOADD) every few seconds. To search, look up the user's cell and its 8 neighbours, then compute exact distance and filter. Shard by city or region.

Design typeahead for 10 k QPS. Senior

Offline job aggregates search logs into top queries per prefix and builds a trie (or prefix → top-10 map). Serve it from memory or Redis, replicated per region, with the CDN caching popular prefixes. Client debounces typing (~150 ms). Trending terms are merged in from a streaming job.

Say this in the interview: "Media goes to S3 via presigned URLs and is served through a CDN. Product search runs on Elasticsearch fed by CDC from Postgres, so the DB stays the source of truth."

Who are you, what may you do

Security: authentication, authorization, encryption

Authentication proves who you are. Authorization decides what you're allowed to do. Encryption keeps data unreadable to anyone in between. Mentioning these briefly in every design shows maturity.

Think of it likean office building. At reception you show ID and get a visitor badge (authentication → token). The badge only opens floors you're allowed on (authorization). The badge expires at 6 pm (token expiry). Confidential papers travel in locked bags (encryption).

Authentication options

  • Session cookie: server stores session in Redis, browser holds a session ID. Easy to revoke. Great for web apps.
  • JWT: self-contained signed token, no lookup needed. Scales across services; hard to revoke early, so keep it short-lived.
  • OAuth 2.0: lets an app act on your behalf without your password ("Allow access to Google Drive").
  • OpenID Connect (OIDC): login built on OAuth ("Sign in with Google").
  • SSO / SAML: one corporate login for all work apps (Okta).
  • API keys for server-to-server; mTLS for service-to-service inside a mesh.
  • MFA / OTP / passkeys for sensitive actions.

Authorization & data protection

  • RBAC: roles (admin, seller, customer) grant permissions.
  • ABAC / ownership: "a user may edit only orders where order.user_id = their id". Always check on the server.
  • Row Level Security: Postgres/Supabase enforce ownership rules inside the DB.
  • Encryption in transit: TLS everywhere, including internal traffic.
  • Encryption at rest: disk/DB encryption with keys in KMS.
  • Passwords: never store them; store bcrypt/argon2 hashes with salt.
  • Secrets: in Vault or a secrets manager, never in code or Git.
  • PCI: never store raw card numbers; use Razorpay/Stripe tokenization.

Interview depth

Authentication vs authorization? Beginner

Authentication: who are you (login, token). Authorization: what can you do (roles, ownership checks). 401 means not authenticated; 403 means authenticated but not allowed.

Sessions or JWTs? Intermediate

Sessions for a single web app: simple and instantly revocable. JWTs when many services or mobile clients need to verify identity without a shared session store. A common hybrid: short JWT access tokens + server-stored refresh tokens that can be revoked.

How do you secure service-to-service calls? Senior

Zero-trust: mTLS between services (a service mesh issues certificates automatically), each service has its own identity, policies say which service may call which, secrets come from Vault with short leases, and the user's identity propagates in a signed token so downstream services can check ownership.

Say this in the interview: "Auth through an identity provider issuing short-lived JWTs, verified at the gateway. Services check ownership on every resource. TLS everywhere, secrets in a manager, and cards tokenized by the payment gateway."

Seeing inside the system

Observability, deployment and operations

You can't fix what you can't see. Observability is how you know the system is healthy, and safe deployment practices are how you change it without breaking it. Most outages come from deploys, so this matters more than it sounds.

Think of it likea car dashboard. Metrics are the speedometer and fuel gauge (numbers over time). Logs are the trip diary (what happened, line by line). Traces are a GPS track of one journey across every road (one request across every service). Alerts are the warning lights.

What to measure

  • Four golden signals (Google SRE): latency, traffic, errors, saturation.
  • RED for services: Rate, Errors, Duration. USE for machines: Utilization, Saturation, Errors.
  • Business metrics: orders per minute, payment success rate. A drop here catches bugs that technical metrics miss.
  • Structured logs in JSON with trace_id, user_id, request_id, so you can search them.
  • Alert on symptoms users feel (error rate > 1%, p99 > 500 ms) based on SLOs, not on every CPU blip.

Safe deployment strategies

  • Rolling: replace servers a few at a time. Default in Kubernetes.
  • Blue-green: run new version beside old; switch all traffic at once; switch back instantly if bad.
  • Canary: send 1% → 10% → 50% → 100% to the new version while watching metrics; auto-rollback on errors.
  • Feature flags: ship code switched off, turn it on per user or percentage (LaunchDarkly, Unleash, GrowthBook).
  • Database migrations: expand-then-contract (add new column, write both, backfill, switch reads, drop old) so old and new code both work.
  • CI/CD: every merge runs tests and deploys automatically (GitHub Actions, GitLab CI, Jenkins, ArgoCD).

Interview depth

Logs vs metrics vs traces? Beginner

Metrics are cheap numbers over time that tell you something is wrong. Traces tell you where in the request path it's wrong. Logs tell you exactly what happened at that point.

How would you roll out a risky change to the payment flow? Intermediate

Behind a feature flag, first to internal users, then a 1% canary watching payment success rate and p99 latency against the old version, automatic rollback if success rate drops by more than a threshold, then ramp up over hours.

What are SLOs and error budgets? Senior

An SLO like 99.9% successful requests over 30 days allows 0.1% failure (the error budget, ~43 minutes). While budget remains, ship fast. If it's used up, freeze risky launches and invest in reliability. It turns "how reliable is enough" into a number both product and engineering agree on.

Say this in the interview: "I'd instrument everything with OpenTelemetry, track the golden signals plus orders per minute, alert on SLO burn rate, and ship through canary deploys with feature flags."

The interview playbook

Every system design question is the same twelve blocks arranged differently. Use this 45-minute structure, and the table below tells you which blocks each famous question leans on.

What interviewers score you on

  • You clarified requirements before drawing.
  • You used numbers to justify choices.
  • Every component has a reason ("Redis here because reads are 100× writes").
  • You named trade-offs and alternatives, not just one answer.
  • You found the bottleneck and the failure modes yourself.
  • You communicated clearly and checked in with the interviewer.

Mistakes that cost offers

  • Jumping into boxes before understanding the problem.
  • Microservices and Kafka for a problem with 1,000 users.
  • Naming tools without explaining why ("I'll use Kafka" and nothing else).
  • Ignoring the single point of failure in your own diagram.
  • Going silent. Think out loud, always.
  • Spending 20 minutes on the easy part and none on the hard part.
